# 뉴스레터 구독 알림 및 주보 자동 발송 기획안

## 목적과 현재 기반

이 기획의 목적은 방문자가 **뉴스레터 구독을 요청하면 이메일을 먼저 데이터베이스와 관리자 구독함에 보관하고**, `info@graceway-baptist.org`로 운영 알림을 전달하며, 확인된 구독자에게 매주 새 주보를 안전하게 안내하는 것입니다. 기존 구독 양식은 이메일·언어를 저장하고, 관리자 화면에는 활성 구독자 목록이 있으며, 주보 PDF는 공개 Google Drive 폴더에서 웹사이트 저장소로 복사되어 행사 페이지에 게시됩니다.

현재 일요일 오전 9시(미국 태평양 시간) 주보 동기화 예약은 이미 활성화되어 있으며, 2026년 9월 13일 실행 성공 기록이 있습니다. 따라서 새 기능은 별도 상시 서버를 만들지 않고, 이 검증된 주보 동기화 흐름에 **“새 이슈를 찾은 뒤 한 번만 발송”** 단계를 추가하는 방식이 적합합니다.

> **핵심 원칙:** 구독 요청, 구독 확정, 발송 시도, 배달 결과, 수신 거부는 서로 다른 상태로 기록합니다. 한 번의 재시도나 예약 작업 중복으로 같은 주보가 두 번 발송되지 않게 합니다.

## 발송 방식 선택지

두 방식 모두 교회 도메인에서 발송하고 `info@graceway-baptist.org`를 회신 주소로 사용합니다. 어떤 방식을 택해도 새 SPF TXT 레코드를 추가하지 않으며, 현재 인증된 Resend 발신 도메인과 Google Workspace 수신함은 그대로 유지합니다.

| 접근 방식 | 운영 방식 | 장점 | 고려할 점 | 비용·설정 복잡도 |
|---|---|---|---|---|
| **A. 웹사이트 구독자 DB + 개별/배치 발송** | 사이트 DB가 구독·수신 거부·발송 이력의 기준이 되고, 발송 서비스는 이메일 전송에만 사용 | 현재 관리자 구독자 화면과 직접 연결되며, 교회가 데이터와 상태를 한곳에서 관리할 수 있음 | 수신 거부 페이지, 발송 이력, 반송 처리 로직을 사이트에 구현해야 함 | 현재 발송 키를 재사용할 수 있어 낮음 |
| **B. 발송 서비스의 연락처·방송 기능 사용** | 사이트 구독자를 발송 서비스 연락처·주제 목록과 동기화하고, 주간 방송을 생성·발송 | 대량 발송 대기열, 구독 해지, 성과 지표를 서비스가 관리 | 사이트 DB와 외부 연락처 목록의 동기화·권한·웹훅 관리가 추가됨 | 발송 서비스의 연락처·방송 권한 설정이 필요해 중간 |

**권장안은 A**입니다. 현재 교회 사이트는 구독자와 주보를 이미 자체 DB에서 관리하고 있고, 새 구독 알림도 같은 관리자 화면에서 확인하려는 요구가 명확합니다. 수백 명 이내의 초기 운영에서는 개별 수신자 발송 기록을 남기는 방식이 투명하고 관리하기 쉽습니다. 향후 구독자 수와 발송량이 크게 증가하면, UI를 바꾸지 않고 B의 대량 방송 기능으로 전환할 수 있도록 발송 서비스 인터페이스를 분리합니다. Resend는 뉴스레터용 대량 방송·연락처·구독 해지 처리를 제공하며, 별도 배치 발송 API는 한 요청에 최대 100개의 이메일을 처리합니다. [1] [2] [3]

## 구독 요청과 관리자 알림 흐름

공개 양식은 지금처럼 이메일과 언어를 받되, 제출 직후 바로 발송 대상이 되는 대신 **구독 확인 대기** 상태로 저장합니다. 이 방식은 타인이 다른 사람의 이메일을 입력해도 즉시 주간 메일을 받지 않게 하는 이중 동의 절차입니다.

| 단계 | 방문자 경험 | DB·관리자 처리 | 이메일 처리 |
|---|---|---|---|
| 1. 구독 요청 | 이메일·언어를 입력하고 “구독 확인 메일을 보냈습니다” 안내를 확인 | `pending` 구독자와 만료되는 일회용 확인 토큰을 저장 | 방문자에게 확인 링크 1통, `info@`에 신규 구독 요청 알림 1통 |
| 2. 확인 링크 선택 | “구독이 완료되었습니다” 페이지 확인 | 상태를 `active`로 변경하고 확정 시각 기록 | 선택적으로 `info@`에 구독 확정 알림; 방문자에게 환영 안내 |
| 3. 중복 요청 | 활성 구독자는 성공 안내만 확인 | 새 중복 행을 만들지 않음 | 불필요한 관리자 알림·확인 메일을 재발송하지 않음 |
| 4. 재구독 | 기존 수신 거부자가 다시 직접 양식에 이메일 입력 | 다시 `pending`으로 전환한 뒤 새 확인을 요구 | 이전 수신 거부를 자동으로 해제하지 않음 |

관리자 화면에서는 기존 **Subscribers** 탭을 “구독 관리함”으로 확장합니다. `확인 대기`, `활성`, `수신 거부`, `반송/억제` 상태, 언어, 가입·확정·최근 발송 시각을 필터링하여 볼 수 있습니다. 연락처 문의(Messages)와 뉴스레터 구독을 한 목록에 섞지 않고, 구독자 탭 안에 구독 요청 감사 이력을 보존하는 편이 개인정보와 운영 목적을 더 명확하게 구분합니다.

## 데이터 모델과 상태 전이

기존 `newsletter_subscribers` 테이블은 기존 활성 구독자를 유지한 채 확장합니다. 과거 `isActive=1` 행은 `active`, `isActive=0` 행은 `unsubscribed`로 마이그레이션하고, 삭제 대신 상태를 보존합니다.

| 저장 대상 | 핵심 필드 | 목적 |
|---|---|---|
| `newsletter_subscribers` 확장 | `status`, `confirmedAt`, `unsubscribedAt`, `lastRequestAt`, `language` | 구독 동의와 수신 가능 여부의 기준 데이터 |
| `newsletter_subscription_tokens` | `subscriberId`, `purpose`, `tokenHash`, `expiresAt`, `usedAt` | 원문 토큰을 저장하지 않는 확인·수신 거부 링크 관리 |
| `newsletter_campaigns` | `issueId` 고유값, `status`, 대상 수, 성공·실패 집계, 시작·완료 시각 | 동일 주보의 중복 캠페인 방지 및 운영 요약 |
| `newsletter_deliveries` | `campaignId`, `subscriberId`, `providerEmailId`, `status`, `attempts`, 시각 | 수신자별 재시도·반송·배달 상태 추적 |
| `newsletter_webhook_events` | `providerEventId` 고유값, 이벤트 유형, 수신 시각, 연결된 배달 행 | 웹훅 중복 수신을 안전하게 무시하고 반송·스팸 신고 반영 |

토큰과 웹훅 원문에는 불필요한 개인 정보를 저장하지 않습니다. 구독 확인·수신 거부 토큰은 암호학적으로 무작위 값을 만들고 해시만 DB에 보관합니다. 발송·반송 오류는 운영에 필요한 코드·분류만 남기고, 이메일 본문이나 외부 서비스의 원문 오류를 앱 로그에 기록하지 않습니다.

## 매주 주보 발송 흐름

일요일 오전 9시(미국 태평양 시간)에 이미 실행되는 주보 동기화는 먼저 Google Drive에서 최신 PDF를 확인하고, 웹사이트 보관함과 행사 페이지에 게시합니다. 이 단계가 성공한 뒤에만 같은 날짜의 `published` 주보를 대상으로 캠페인을 생성합니다. 주보가 없거나 최신 파일 날짜가 해당 주일과 다르면 **이전 주보를 다시 보내지 않고** `info@`에 “이번 주 발송 보류” 알림만 남깁니다.

발송 이메일은 PDF를 첨부하지 않고, 행사 페이지의 주보 미리보기·다운로드 링크로 안내합니다. 이 방식은 모바일 수신함 용량과 첨부파일 제한을 피하고, 발송 후 교정된 PDF도 한 링크에서 관리할 수 있습니다. Resend 배치 발송 API는 첨부를 지원하지 않으므로 링크 중심 구성은 현재 전송 방식과도 일치합니다. [3]

| 순서 | 예약 실행 처리 | 중복·실패 안전장치 |
|---|---|---|
| 1 | 최신 주보 동기화 | 기존과 같이 실패 시 마지막 공개 주보 유지 |
| 2 | 해당 주일의 공개 이슈 확인 | 이슈 날짜가 오늘과 다르면 발송하지 않음 |
| 3 | 고유한 캠페인 행과 수신자별 대기 행 생성 | `issueId`와 `campaignId + subscriberId` 고유 제약으로 중복 차단 |
| 4 | `active` 구독자만 언어별 템플릿으로 발송 | 요청별 멱등성 키와 전송 ID 저장 |
| 5 | 결과 집계·`info@` 요약 알림 | 성공·실패 수만 알리고 구독자 전체 주소를 이메일에 넣지 않음 |
| 6 | 반송·스팸 신고 수신 시 상태 반영 | 이후 캠페인 대상에서 자동 제외 |

현재 예약 처리의 2분 실행 제한을 고려해 초기는 소규모 배치로 처리합니다. 구독자가 늘어 한 번의 실행에 안전하지 않은 규모가 되면, 대량 방송 기능으로 전환하거나 같은 캠페인의 미처리 수신자를 후속 예약 실행에서 이어 보내도록 확장합니다. 예약 실행은 항상 멱등적으로 만들며, 같은 이슈가 재동기화되거나 플랫폼이 재시도해도 재발송하지 않습니다.

## 수신 거부, 반송 및 개인정보 보호

모든 주간 이메일의 본문 하단에는 명확한 **수신 거부** 링크를 넣고, 이메일 클라이언트의 원클릭 수신 거부를 지원하는 헤더도 설정합니다. 원클릭 요청은 `POST`로 처리하고 즉시 200/202을 반환하며, 이메일 본문 링크는 일반 브라우저 확인 페이지로 연결합니다. 자체 구독자 목록을 운영할 때 이 헤더와 처리 흐름을 제공해야 한다는 Resend 안내를 따릅니다. [4]

Resend는 배달, 반송, 실패, 스팸 신고 등 이메일 이벤트 웹훅을 제공하므로, 2단계 후반에는 `email.bounced`, `email.complained`, `email.delivered`만 우선 수신하여 구독자·배달 이력을 갱신합니다. 웹훅은 중복 도착할 수 있으므로 제공되는 이벤트 식별자를 고유값으로 저장해 한 번만 처리합니다. [5] [6]

> **발송 정책 제안:** 발신자 `Graceway Weekly Newsletter <newsletter@graceway-baptist.org>`, 회신 주소 `info@graceway-baptist.org`, 제목 `Graceway Weekly Newsletter · 2026.09.13` 또는 한국어 수신자용 `그레이스웨이 주간 주보 · 2026.09.13`을 사용합니다. 주소는 확인된 교회 도메인에서 발송하고, 회신은 실제 교회 Gmail 수신함으로 받습니다.

## 구현 단계와 승인 지점

| 단계 | 구현 범위 | 실제 이메일 발송 여부 | 승인 필요 사항 |
|---|---|---|---|
| 1. 구독 관리 | 구독 상태·확인/수신 거부 토큰, 관리자 구독 관리함, `info@` 운영 알림, 방문자 확인 이메일 | 확인 메일 1통만 테스트 | 발신자 정책·이중 동의 채택 |
| 2. 캠페인 준비 | 주보 이슈-캠페인-배달 이력, 이메일 템플릿, 주보 링크, 관리자 미리보기·테스트 발송 | 관리자 지정 테스트 수신자에게만 | 이메일 문구·발신자·테스트 수신자 |
| 3. 자동 발송 | 기존 일요일 9시 주보 동기화 뒤 발송, 보류·재시도·요약 알림 | 실제 활성 구독자에게 발송 | 자동 발송 활성화 전 최종 승인 |
| 4. 배달 상태 강화 | 반송·스팸 신고·배달 웹훅, 자동 억제 및 관리자 이력 | 기존 발송에 상태 기록 추가 | 웹훅 서명 비밀값 등록 및 대시보드 설정 |

## 이번 단계에서 결정할 사항

구현을 시작하기 전 아래 네 가지를 승인해 주세요.

1. **발송 방식:** 현재 DB 중심 방식(A) 또는 외부 연락처·방송 방식(B) 중 선택합니다.
2. **동의 방식:** 권장안인 이메일 이중 확인을 사용할지 결정합니다.
3. **발신자 정책:** 위에 제안한 `newsletter@` 발신자와 `info@` 회신 주소를 승인합니다.
4. **자동 발송 시점:** 매주 일요일 오전 9시 미국 태평양 시간을 기준으로 하되, 주보가 없으면 발송을 보류하고 운영 알림만 보내는 정책을 승인합니다.

자동 발송을 활성화하기 전에는 실제 구독자에게 보내지 않고, 승인된 테스트 주소로 구독 확인·수신 거부·주보 링크·중복 방지 흐름을 검증합니다.
